# Rules

> Positioning: collects only the rules that apply to `SDS.Contracts` itself, each executable and checkable. Global rules are in ModuleRules.en.md and are not repeated here (the authoritative rule text migrated in from history is at the end of this file under "Normative rule text (authoritative)"); every rule comes with a checking method.

|---|---|---|---|

## Normative rule text (authoritative)

> The following normative sentences were migrated in from the global rule index; `SDS.Contracts` must comply with them and C1–C8 do not cover them. They are reproduced verbatim as the authoritative text. Checking follows the corresponding C rule together with ModuleInterfaces.en.md and PatchInventory.en.md.

| ID | Normative text | Relationship to this module |
|---|---|---|
| W26 | Old saves → new version must be readable; no data loss takes precedence over an unchanged format; no promise of new version → old version. | `SDS_StockKey` writes only `defName` / `stuffName` as of 2026-11-16; the legacy nodes `thingDef` / `stuff` are read-only, never written (saves written before 2026-11-13 remain readable); all DTO defaults must be able to read old saves. |
| W27 | Rollback uses channel-specific fallbacks (preserved `ReturnPreserved`, virtual `ReturnVirtual`); a generic `Return` is forbidden. | `SDS_StockChannel` provides the explicit channel parameter for the unified return facade. |

## Supplementary basis (version family)

- Key equality and hashing share one basis: `SDS_StockKey.SameAs` compares via `EffectiveStuffName` when either side's stuff is unresolved (`stuff == null`); `GetHashCode` likewise uses the names only, and "equal but differently hashed" must never occur. Aggregate display keys (`CategoryKeyOf`) are for display / grouping only and must never be written into the ledger or the disablement sets. Check: the key-equality and hash-consistency cases in `SDS.Tests` `ContractTests`.
- `SDS_ReadVersions` supplies all six versions at once: `tick` / `mirror` / `endpoint` / `stock` / `reservation` / `filter`; of these, snapshots judge invalidation only by `tick` / `mirror` / `endpoint` / `stock`.
- `CanReach`, transaction reservations, and filtering do **not** enter snapshots: reservations belong only to availability judgment, filtering only to the read-only query cache, and reachability is recomputed on demand every time.
- The snapshot cache refreshes on a 60-tick fallback; even when versions have not advanced, it will not stay stale for long.
- `tick` and the individual versions must be captured in one batch (a single `CaptureReadVersions`); a previously captured `tick` must never be stitched together with versions captured later.
