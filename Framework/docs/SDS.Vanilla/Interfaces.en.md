### 4.1 Container and Job Assignment Contracts: IHaulDestination / IStoreSettingsParent / IThingHolder / IHaulEnroute / IHaulSource (originally §1)

- **Vanilla mechanism**: `IHaulDestination` decides whether a Thing participates in non-SlotGroup destination search (`Accepts` is the intake gate, `HaulDestinationEnabled` decides visibility); `IStoreSettingsParent` provides `StorageSettings` and priority for vanilla sorting; `IThingHolder`'s `GetDirectlyHeldThings` is the container's direct content and `GetChildHolders` its recursive subtree; `IHaulEnroute.SpaceRemainingFor` serves in-transit reservations; `IHaulSource` lets entry points such as `WorkGiver_DoBill` recursively read content along holders.
- **Where it hooks in**: `ISDS_StorageEndpoint` inherits these four interfaces at once, implemented by `Building_SDS_Core` / `Building_SDS_Port` (`SDS_Buildings.cs`). An endpoint must never implement `ISlotGroupParent`: once implemented, the container branch of vanilla hauling can never hold (interface comment in the same file).
- **Write-through semantics**: `SDS_EndpointBuffer.TryAdd` and `GetCountCanAccept` share the same `Accepts` hard gate; after successfully entering the buffer only this one item is processed, and on failure `EjectToMap` is called — goods are never swallowed across ticks (`SDS_EndpointBuffer.cs`). `CanAcceptNow` unconditionally lets save leftovers through during load time (`Scribe.mode != Inactive`) and in non-`Playing` states; flushing happens only under `Playing` + `Inactive`.
- **Vault**: `Building_SDS_Vault` implements `IHaulDestination` + `IStoreSettingsParent` + `IHaulSource`, with `HaulDestinationEnabled=false` and empty direct content, projections attached via `GetChildHolders`; this makes it both a count-only `SlotGroup` and prevents stock from being counted twice in direct-content enumeration (`SDS_Buildings.cs`).
- **Warehouse proxy criterion (W53)**: the storage facts of mirrors are provided only by the per-map `SDS_MirrorHaulDestination` proxy — `Patch_SDS_MirrorHaulDestination` makes `CurrentHaulDestinationOf(mirror)` return the proxy (`Accepts` always true, `HaulDestinationEnabled=false`, priority synced to the save-level value in `GetStoreSettings`), so that `IsInAnyStorage` / `IsInValidStorage` are true and `CurrentStoragePriorityOf` takes the save-level priority. The vault's own `StorageSettings` does not participate in this determination and must not be written as a second copy.
- **Mirrors cannot be deposited (W53)**: `SDS_EndpointUtility.IsDepositable` is the sole criterion (non-mirror + `SDS_Rules.CanDeposit`); the endpoint's `IHaulDestination.Accepts`, `SDS_DepositService`'s job assignment gates, and manual deposits all go through it, and mirrors are always rejected. Otherwise the W52 outflow jobs would be rewritten by deposit competition, and endpoints would be treated as outflow destinations for mirrors.
- **Mirror placement**: mirrors do not pick cells themselves; their position is provided by the hidden vault. `Building_SDS_Vault.FindVaultCell` accepts only cells that are "on the map, not fogged, standable, no building, no `Zone`, no `SlotGroup`", and before placing checks `GetMaxItemsAllowedInCell > GetItemCount`, otherwise `ScheduleRetry` (`SDS_Buildings.cs`).
- **Region exception**: `IsFreeCell` excludes only Zones and SlotGroups, not Regions, so the vault / mirrors may land inside a region; placement inside a region must still pass the remaining validations.
- **Direct-content enumeration**: `GetAllThings(lookInHaulSources: true)` reads only a holder's single layer of direct content; `ApparelSource` treats the vault as an empty apparel source to keep projections from being treated as wearable items.
- **Warehouse proxy semantics**: `Accepts` always true, `HaulDestinationEnabled = false`, priority follows global settings, `Position` always `Map.Center` (placeholder only; does not participate in distance or placement determination).
- **Endpoint candidate enumeration**: `SDS_EndpointProvider.AppendCandidates` only enumerates "building facts + pawn chip facts" and does not judge `Operational` during enumeration; usability is judged in real time by Core's hard gate. The building list is cached by `EndpointVersion`, pawns are scanned in real time every tick; the self port is appended last (`allowSelf` and the pawn's own port usable), with distance computed in real time from the reference point; folding into self is completed by W62 after the endpoint wins.

### 4.3 ResourceCounter.UpdateResourceCounts — the Resource Bar (originally §3)

- **Vanilla mechanism**: the resource bar sums the physical items counted by `CountAsResource` per `SlotGroup.HeldThings`, caches the result in `countedAmounts`, and refreshes periodically via `ResourceCounterTick`.
- **Where it hooks in**: there is only 1 mirror per category per map, its `stackCount` represents the whole category's stock, and preserved true bodies do not spawn, so a purely physical count misses ledger quantities. `Patch_SDS_ResourceCounterWithGrid` applies a Postfix to `UpdateResourceCounts`, filling the gap per `SDS_Exposure.InjectedOnCounter`; `Patch_SDS_ResourceCounterFastRefresh` applies a Prefix to `ResourceCounterTick`, triggering one refresh only within the 30-tick throttle, without changing the vanilla result (`Patch_VanillaSeams.cs`).
- **Criterion ownership**: whether this map exposes the stock is decided by `SDS_Exposure.MapExposesGrid` (G + usable endpoints on this map); the patch only consumes `SDS_Exposure` and does not derive "how much to add" by itself (`SDS_Exposure.cs`).
- **Correction formula**: `CounterAdjust = (exposed ? ledger quantity : 0) − physical exposure`; physical exposure comes from the mirrors' actual stack amounts, so the portion vanilla has already counted is first deducted back. When a mirror exists but vanilla did not count it (fog / stale), the target counts as 0 and the ledger is not used as a fallback. The def-level aggregate `InjectedOnCounter` = the corrections of all virtual keys of that def + the corrections of keys existing only in the mirror table + the preserved quantity when exposed.
- **Fast refresh**: `TryBeginCounterRefresh` lets a refresh through only when "not `now % 204 == 0` (vanilla recalculates the whole table on that tick) + at least one of the five versions — mirror / endpoint / stock / reservation / filter — has changed + ≥ 30 ticks since the last time + this map is exposed"; otherwise it is handed back to vanilla `ResourceCounterTick`.

### 4.4 WealthWatcher.CalculateWealthItems — Wealth (originally §4)

- **Vanilla mechanism**: `WealthWatcher.CalculateWealthItems` tallies map item wealth via `ThingOwnerUtility.GetAllThingsRecursively(map, HaulableEver, allowUnreal:false, WealthItemsFilter)`.
- **Where it hooks in**: mirrors spawned on vault cells would be counted, preserved true bodies that do not spawn would be missed, and when the "exclude from colony wealth" setting is on, the mirror wealth of all maps must also be deducted. `Patch_SDS_WealthNormalize` applies a Postfix to `CalculateWealthItems`, calling `SDS_Exposure.WealthAdjust` with the result clamped to 0; `Patch_SDS_WealthItemsFilterProjection` handles `WealthItemsFilter`'s filtering of `SDS_MapLevelHolder` / projections (`Patch_VanillaSeams.cs`, `Patch_Mirrors.cs`).
- **Correction formula**: `WealthAdjust` returns three mutually exclusive branches — ① `excludeGridFromWealth` on: `−this map's mirror wealth` (no preserved added on any map); ② this map not exposed or not the canonical map: `−this map's mirror wealth`; ③ canonical map: `ledger virtual wealth + preserved wealth − this map's actual mirror wealth`. The result is clamped to 0 in the patch. Mirror wealth counts only mirror stacks that are spawned, not fogged, and `EverHaulable`.
- **Canonical map**: `CanonicalExposureMap` prefers the player's main base, otherwise the first map with `MapExposesGrid`; the same stock is counted once only on the canonical map to avoid duplication across colonies.
- **Holder filtering**: `WealthItemsFilter` replicates the vanilla Pawn criterion for `SDS_MapLevelHolder` (player faction and not a quest temporary resident), and always lets `SDS_ProjectionHolder` through (projections are already handled by normalization deductions / additions).

If the driver finds the runtime plan empty while the ledger still has preserved reservations, it rebuilds the plan per W47 from the unique bucket in the container; if no unique bucket is found or the amount is short, it fail-closes.

### 4.9 Materialization Semantics: CompRottable / ThingOwner / Thing.SplitOff (originally §9)

- **Vanilla mechanism**: `ThingOwner` is the unified entry point for containers / inventories / transport pods / caskets / gene banks (`TryAdd`, `TryAddOrTransfer`, `TryTransferToContainer`, `GetCountCanAccept`); `Thing.SplitOff` produces a new item of the specified quantity; `CompRottable` stores rot progress; `Thing.Destroy` is irreversible consumption.
- **Where it hooks in**: mirrors are whole-category aggregate stacks; partial takes must produce a real item with the original `HitPoints` / `RotProgress`, whole-stack takes must convert the mirror itself into the true body, and all container writes must swap mirrors for true bodies exactly once. `SDS_MirrorPhysicalOps.TryTakePhysical` builds the item with `SDS_OutputUtility.MakeDisplayThing`, adjusts `stackCount`, writes back HP / rot, and calls `MarkChanged`; `TryTakeWholePhysical` does `ForgetMirror` / `Unmark` / restores `CompRottable.disabled` / `DeSpawnOrDeselect`. `SDS_Transmission`'s `Patch_SDS_OwnerTryAdd` / `Patch_SDS_OwnerTryAddOrTransfer` swap mirrors for true bodies at container entry; `SDS_EndpointBuffer` passes `Accepts` first at buffer entry (`SDS_Mirrors.cs`, `SDS_Transmission.cs`, `SDS_EndpointBuffer.cs`; ModuleInterfaces.en.md 4.3).
- **The W51 preserved gap in multi-slot recipes**: vanilla `WorkGiver_DoBill.TryFindBestBillIngredients` picks ingredients only from physical items on the map, while `TryFindBestBillIngredientsInSet` requires **all recipe slots** to be satisfiable from the passed-in candidates; preserved true bodies are not on the map, so single-channel candidates can never fill the gap (typical case: resurrecting a mechanoid = 1 corpse + N steel). The only approach is: after the vanilla search fails, take true bodies from the preserved channel slot by slot per the vanilla-returned `missingIngredients`, materialize them at `SDS_VirtualBillFallback.RootCell` (= the `InteractionCell` when the building has one, otherwise the building's own cell; the `IngredientPlaceCellsInOrder[0]` in source comments is only a semantic explanation and the code does not read that property), then re-run the vanilla search in the same tick; afterwards vanilla itself hauls and deposits them via `DepositHauledThingInContainer`. The count = `Math.Max(1, IngredientCount.CountRequiredOfFor(...))` clamped to that true body's `stackCount`. **No source-exclusion mark is applied**: the materialized instance is taken over by the vanilla Job within the same tick; if the player then cancels the bill, the corpse stays on the ground and can be automatically re-absorbed by the endpoint (self-healing). Materialization requires `billGiver is Building` and `HasReachableEndpoint(pawn)` (**`ingredientSearchRadius` is not applied**); if any item cannot be placed, the already-placed items of this batch are returned to the ledger. Writing work table / gestator containers directly is forbidden, and reviving the deleted batch reservation / batch materialization mechanisms is forbidden. Implementation anchor: `SDS_PreservedBill.cs` (`TryMaterializePreservedGaps` + the `Patch_SDS_PreservedBillIngredients` re-entry guard).
- **Projections are not real containers**: `TryAdd` / `GetCountCanAccept` are always false / 0 for projections; `Remove` directly returns false beyond `stackLimit`; `Contains` is not guaranteed false — the internal list is empty before the first read, and after any read that triggers `EnsureFresh` (`Count` / enumeration / `IndexOf` / `Remove`) it may hit the mirror reference; third parties must switch to `Take` / `SplitOff`.
- **Non-pawn receiver gate (S18)**: `SDS_Transmission`'s `TryAdd` / `TryAddOrTransfer` judge faction via `OwnerPawn` before a mirror enters a container; equipment / apparel / inventory belong to known Pawn owners and are rejected outright when the setting is on.
- **S18's actor-less residue**: `Thing.SplitOff` / `TryAbsorbStack` / generic `ThingOwner` have no Pawn context and cannot directly judge faction; they rely on the search / reachability / Job gates to block first, and third parties bypassing those gates to operate on mirrors directly is outside the guarantee.

### 4.10 GameComponent Lifecycle and Save Timing (originally §10)

- **Vanilla mechanism**: a `GameComponent` is constructed once per `Game`, participates in save `ExposeData`, runs `FinalizeInit` after load, and `GameComponentTick` every tick. Since 2026-11-16 this module no longer has a `MapComponent` (the old protected-output shell has been retired), and all save state is concentrated in the single `SDS_GameComponent_Grid` (ModuleInterfaces.en.md 4.1, 4.4).
- **Where it hooks in**: the ledger must hang on the `Game` rather than a Mod static field, so that it is saved with the save, restored at load, and cleaned up on game switch. `SDS_GameComponent_Grid`'s construction order is fixed as `SDS_StaticState.ResetAll()` → `SDS_Core.CreateLedger()` → `new SDS_VanillaState()` → set `Instance` → `SDS_Core.Attach(Ledger)` (`SDS_GameComponent_Grid.cs`).
- **ExposeData nodes**: `Ledger.ExposeData()` (the Core ledger node) + `State.ExposeData()` (this module's 7 nodes) + `sdsReclaim` (the component-level reclaim ledger, `Deep`). When saving, `SDS_ReclaimRegistry.ExportTo` first exports to a staging list before writing; `PostLoadInit` calls `ImportFrom` immediately, with auditing deferred to `FinalizeInit`. No fallback ledger rebuilding and no re-attaching of `SDS_Core`.
- **FinalizeInit order**: `State.CleanupLoadedMirrors()` (destroys old mirrors after map spawn) → `BeginMirrorJobTargetRemap()` (W60) → `TryRemapMirrorJobTargetsImmediately()` (immediate synchronous rebuild + remap; kept until Tick on failure) → `BeginTransportLoadRestore()` (W48) → `TryRestoreTransportLoadRowsImmediately()` (attempts W48 row restoration once immediately, for W47 to resolve container buckets) → `SDS_TransportVirtual.RebindLoadedDisplayKeys()` (re-seals persisted display things inside container rows) → trimming duplicate copies in pawn inventories / held items + worn preserved warning → `sdsReclaim` fallback re-import → `SDS_ReclaimRegistry.AuditRestored()` → `SDS_Core.AuditReservations(ReclaimOwnerAlive)` → set load-diagnostics pending / record map signatures → `SDS_OutputCommand.SyncForbiddenToPreserved()` → output the load diagnostics once.
- **Tick order**: see §1.1; the essence is "ledger → state → load diagnostics → first-save notice → reservation audit / reclaim sweep (250) → map signature + stock nudges (30) → structure reconciliation (250, correcting endpoint priorities at the end)".
- **Load diagnostics / first-save notice**: `TryLogLoadDiagnostics` runs the Category-B count report once after maps are ready (in developer mode it additionally runs the full read-only self-check); `TrySendIntroNotice` sends a `PositiveEvent` once per save, persisted with `introNoticeShown`.
- **Holder boundary**: `SDS_GameComponent_Grid` does not implement `IThingHolder`; preserved true bodies are held by Core's private owner; `Map.GetChildHolders` only iterates `map.components`, so removing `IThingHolder` has no effect on Map-level enumeration (ModuleInterfaces.en.md 4.1).
- **Old save shell retired (2026-11-16)**: `MapComponent_SDS_ProtectedOutputs` and `sdsProtectedOutputs` served only saves before 2.4 (2026-10-26 21:54) and have been removed per [CompatibilityRetirement.en.md](CompatibilityRetirement.en.md); old saves no longer read that node, and new saves write only `sdsReclaim`.
- **Reclaim ledger (C1/C8)**: both `SDS_ReclaimRegistry` and the `sdsReclaim` node live in this module; `SDS_GameComponent_Grid` is the sole read/write point (the node sits alongside this ledger, and old saves' same-named node goes through the same read path): `PostLoadInit` → `ImportFrom`; `FinalizeInit` fallback re-import → `AuditRestored` (job target / hand-held ingredient audit + protected-output sweep). `FinalizeInit` and the 250-tick audit pass the liveness-check delegate via `SDS_Core.AuditReservations(ReclaimOwnerAlive)`, and `SDS_ReclaimRegistry.Sweep` is called every 250 ticks (sweeping protected outputs only).

### 4.11 Why Work Types (WorkTypeDef / WorkGiver) Are Not Modified (originally §11)

- **Vanilla mechanism**: `WorkTypeDef` defines work categories and priorities, `WorkGiverDef` attaches WorkGivers to work types, and ThinkTree `JobGiver`s assign jobs to pawns.
- **Where it hooks in**: this assembly adds no `WorkTypeDef` / `WorkGiverDef`; it only applies Postfixes to the existing `WorkGiver_Haul`, `JobGiver_Haul`, `HaulAIUtility`, and each WorkGiver's `JobOnThing` / `HasJobOnThing`. What is added are only JobDefs like `SDS_DepositToGrid` and their JobDrivers (ModuleResponsibilities.en.md §6; PatchInventory.en.md 3·6). For the W63 folding / yielding variant see the 4.5 boundary.
- **Boundary**: custom dispatch that never goes through `WorkGiver.JobOnThing` / `HasJobOnThing` is not covered and needs a separate initiative; third-party haulers with their own job factories that do not call `HaulAIUtility` are also not covered by the function-level exits.

### 4.12 Known Boundaries (originally §12)

- Local `ThingGrid` / `GenRadial` radius searches do not convert distances to access points; `RegionwiseBFSWorker` is not patched separately.
- **Atomic fuel**: `FindEnoughReservableThings` has no access-point fallback; `FindFixedIngredientCount` still uses region BFS and is only partially covered.
- **En-route merging**: `Toils_Haul`'s en-route merging may select a mirror, rerouting the Job to pick up at the endpoint; this is an expected path, not a missed assignment.
- **Caravans in transit**: with `Map == null` and no physical port, only caravan formation loading or remote trading works; endpoint deposit / withdrawal is unavailable.
- **DoBill ingredient distance**: both DoBill's region BFS and `TryFindBestIngredientsInSet` use `thing.Position` (the vault cell) to compute distance / radius, so mirrors may be excluded or ranked lower because the vault exceeds `ingredientSearchRadius`.
- **Loading deficit differs from formation**: formation uses `CountToTransfer − physical quantity not held by a holder`; loading uses `CountToTransfer − in-transit quantity` (in-transit = the `initialCount` of vanilla `HaulToTransporter` / `HaulToPortal`). W25 explicitly defines the two as different criteria that must not be interchanged: loading is not deducted by map physical quantities, because vanilla only lets the Hyperdimensional Space take over when no loadable physical items can be found.
- **Loading multi-identity does not fail-close**: on the formation side, multiple virtual keys / multiple preserved buckets in one row trigger `Fail` and zero out the whole row; on the loading row-selection side, when one row has multiple virtual keys the first usable key is taken, and with multiple preserved buckets any bucket fetchable for the whole trip may be chosen, without zeroing (this difference between formation and loading is registered respectively in [Rules.en.md](Rules.en.md) §12.6).
- **W47 load-time rebuild**: runtime plans do not cross saves; if the driver's first toil finds the plan empty while the ledger still has preserved reservations, it rebuilds the plan with `TakePlan` from the unique bucket in the container by reservation key, and after registering it as a runtime plan continues along the original reservation and materialization path; when no unique bucket is found or the amount is short, `SDS_Diag.Fail` + fail-closed, with stock and reservations untouched. `FinalizeInit` attempts W48 row restoration once immediately, shortening the wait window.
- **Fail-closed on missing snapshot**: `JobOnTransporter` / `JobOnPortal` reassign only when the same-tick `HasJob` snapshot hits; when missing, `FindThingToLoad` / `TrySelectLoadRow` are not called, the vanilla result is kept as-is with a one-time `Warn`, and the next tick's `HasJob` re-registers. When third parties bypass `HasJob` and call `JobOn` directly, the Hyperdimensional stock is not used.

### 4.13 Trading / Launching / Remote Buying & Selling

- **Vanilla mechanism**: `TradeDeal.Reset` builds the `Tradeable` list; `TryExecute` executes deals uniformly; `Tradeable.ResolveTrade` settles row by row; `Dialog_Trade.Close` wraps up. Launching goes through `TradeUtility.AllLaunchableThingsForTrade` (read) and `LaunchThingsOfType` (write); remote buying and selling goes through `Settlement_TraderTracker` / `Caravan_TraderTracker`'s `ColonyThingsWillingToBuy` and `GiveSoldThingToPlayer`.
- **Hook points**: `TradeDeal.Reset` (Prefix cleanup + Postfix injection), `TradeDeal.TryExecute` (Prefix validation), `Tradeable.ResolveTrade` (low-priority Prefix replacement), `Dialog_Trade.Close` (Postfix cleanup), `TradeUtility.AllLaunchableThingsForTrade` (Postfix append), `TradeUtility.LaunchThingsOfType` (Prefix deducts the shortfall), `Settlement_TraderTracker` / `Caravan_TraderTracker`'s `ColonyThingsWillingToBuy` (Postfix append) and `GiveSoldThingToPlayer` (Prefix credits) (`Patch_Trade.cs`).
- **List injection**: the virtual leg iterates `Snapshot(0)`, skips `key.preserved`, requires `GetTradableCount > 0` and `PlayerSellableNow`, sets `stackCount = ClampTakeToAvailable(int.MaxValue, available)`, then clamps once more by `room = int.MaxValue − already held`; the preserved leg builds one display thing per bucket via `SDS_PreservedBuckets.Build(..., tradeGrouping:true, tradableBudget:true)`, with shrunken stacks in their own buckets. Only the trade panel's `BuildTradePreservedDisplays` writes the display thing / bucket registry; the beacon's `BuildPreservedDisplays` builds read-only.
- **Execution validation (read side, R15 / R16)**: iterates only rows with `ActionToDo == PlayerSells`, consuming `thingsColony` item by item in vanilla consumption order; the budget comes from `GetTradableCount` (total − reserved, forbidden items not filtered), and preserved rows additionally run a feasibility dry-run with `SDS_PreservedBuckets.TakePlan`. Any short row → pops "the stock has changed" and cancels the whole trade; validation neither reserves nor deducts.
- **Settlement (write side)**: `ResolveTrade` replaces only when this row actually consumed display things: display things are swapped for equal-quantity true bodies in vanilla order — the virtual leg goes through `SDS_Rules.TryWithdraw` (a `SpawnedTarget` transaction), the preserved leg runs `TakePlan` on the registered bucket then `TryWithdrawPreservedExact`. On a replacement exception, the already-taken true bodies are rolled back by channel and the row is skipped; display things are never handed to the trader.
- **Beacon launching**: the read side appends virtual and preserved display things only when `trader == null`, this map has a powered comms beacon, and this map exposes the ledger (preserved excludes shrunken stacks); the write side's `LaunchThingsOfType` deducts `debt − onMap` from the ledger when map physical items are insufficient, reducing by whatever amount is deducted. Calls carrying a `TradeShip` do not enter this deduction branch.
- **Remote buying**: requires chip B, player faction, the cross-map tech `SDS_AdvancedPrecisionSuperStorage` completed, and `SDS_Rules.Available`. Bought goods go `SplitOff` → `PreTraded` → `SDS_Rules.TryDeposit` (`SDS_DirectDepositPort`); on success vanilla delivery is suppressed, on failure the split is restored and the goods are handed back to vanilla.
- **Wrap-up**: `Reset()` / `Dialog_Trade.Close` only release display thing and bucket references without destroying physical items; display thing instances are cached globally by key / by bucket, with `stackCount` shared across windows.

### 4.14 Bills / Medical / Genes / Growth Vats / Caskets / Installation

- **Vanilla mechanism**: `WorkGiver_DoBill` first filters candidates with `IsUsableIngredient`, then picks ingredients via `TryFindBestBillIngredients` (falling back to `TryFindBestFixedIngredients` on failure), and finally generates the Job with `TryStartNewDoBillJob`; genes, xenogerms, growth vats, caskets, and installation each go through their own UI / container entry points.
- **Medical gate (S17)**: `Patch_SDS_MedicalIngredientGate` intercepts only "medicine + `Bill_Medical` + patient is a Pawn"; the judgment lives solely in `SDS_MedicalGate.Allows` (underneath, `SDS_MedicalCareAdapter` calls vanilla `GetMedicalCareCategory(...).AllowsMedicine`); non-medicine / non-Pawn billGivers always pass. The virtual leg, the preserved leg, W51, and `FindBestMedicine` all go through the same gate.
- **DoBill ingredient-selection order**: vanilla success → no change; vanilla failure → ① virtual leg `SDS_VirtualBillFallback.TrySupplyVirtualIngredients` (candidates take only this map's mirrors, required to be within `ingredientSearchRadius` of `RootCell`, with a reachable endpoint, passing `SDS_MedicalGate` / `IsFixedOrAllowedIngredient`, invoking vanilla `TryFindBestBillIngredientsInSet` via reflection); ② preserved leg `TrySupplyPreservedIngredients` (candidates come from ledger true bodies, **no search radius applied**, only requiring a reachable endpoint; multi-item plans are also constrained by total weight ≤ carry capacity); ③ W51 `TryMaterializePreservedGaps` (only `Building` work tables; materializes slot by slot to interaction cells; the same tick re-runs the vanilla search guarded by `rerunning`, rolling back the batch on failure).
- **Fixed ingredients**: `TryFindBestFixedIngredients` has only the virtual leg, reusing vanilla's `_NoMixHelper` probe and the same `RootCell` / radius criteria.
- **Pure-preserved Job**: the `TryStartNewDoBillJob` Postfix changes the job to `WithdrawPreservedForBill` only when "the result is still `DoBill` and all of `targetQueueB` are unspawned preserved true bodies" (A = endpoint, B = work table); it returns null when no reachable endpoint exists, leaving no broken Job.
- **Preserved pickup driver**: first reserves the pickup point, work table, and interaction cell (on failure → `nextTickToSearchForIngredients = now + 60` backoff), then books the preserved plan per queue, and after reaching the endpoint does `TryWithdrawPreservedExact` + `MarkProduced`, taking the first item into hand and the rest into the inventory, finally handing back to vanilla `DoBill` (clearing the backoff). Any failure returns the already-taken true bodies through the preserved channel; items are never swallowed.
- **Genepacks**: `Dialog_CreateXenogerm` registers the current assembler at construction; the `Building_GeneAssembler.GetGenepacks` Postfix injects only once per window opening, extracting preserved `Genepack`s from the ledger and `TryAdd`ing them into `CompGenepackContainer`s with free space; if the container rejects, `ReturnThing(Preserved, Ground)`.
- **Xenogerms**: `Recipe_ImplantXenogerm.AvailableOnNow` becomes selectable when the stock has a preserved Xenogerm and a reachable endpoint; `Dialog_SelectXenogerm` appends ledger true bodies to its private list at construction; the `Xenogerm.SetTargetPawn` Prefix materializes the true body after player confirmation, showing a message and blocking vanilla on failure.
- **Growth vats**: `Building_GrowthVat.GetGizmos` appends "Implant embryo from Hyperdimensional Space" (grayed out without power); the `SelectEmbryo` Prefix materializes the selected preserved embryo to the interaction cell before handing over to vanilla.
- **Caskets / graves**: the `Building_Casket.TryAcceptThing` Prefix first extracts from the ledger; the Finalizer returns via the preserved channel when vanilla rejects or throws.
- **Install blueprints**: the `GenConstruct.PlaceBlueprintForInstall` Prefix materializes the preserved shrunken item, cancels the old blueprint for the same innerThing, then continues with the true body; the install-panel path is uniformly canceled / rolled back by `SDS_InstallBlueprintGuard` (W32).
- **Division of in-transit marking**: any path that materializes and then waits on the map for a future vanilla assignment (xenogerms, growth vat embryos, install shrunken items, preserved loading materialization) applies `MarkProduced`; W51's materialization is taken over by the vanilla Job within the same tick, and virtual loading materialization is handed directly to vanilla pod loading, so these two explicitly do **not** get marked; the two path types must not be interchanged.

### 4.15 The Preserved Consumption Bridge (medicine / food / weapons / apparel)

- **Vanilla mechanism**: `HealthAIUtility.FindBestMedicine`, `FoodUtility.TryFindBestFoodSourceFor`, `JobGiver_PickUpOpportunisticWeapon.TryGiveJob`, and `JobGiver_OptimizeApparel.TryGiveJob` return failure / null when "no usable item exists on the map"; `StoreUtility.IsInAnyStorage` decides whether a physical item is considered in storage.
- **Hook points**: one Postfix each for the four decision entry points above (low priority), plus a `StoreUtility.IsInAnyStorage` Postfix (`SDS_PreservedOffer.cs`). All take over only when vanilla returns "none" and do not change anything when vanilla has a result.
- **Materialization and lifecycle**: the preserved leg `SDS_PreservedOffer.TryOffer` screens ledger true bodies item by item (resolvable, not forbidden, available > 0, no reservation on the same key), takes 1 by score → `TryWithdrawPreservedExact` → `SDS_OfferBridge.TryPlace` places it at the nearest reachable access point; independently placed items get `MarkProduced`, are unforbidden, have `CompRottable` frozen, and register an offer. When the landing spot merges into an existing same-kind stack, only a cooldown is recorded — no tracking, no marking.
- **Timeout and return to ledger**: offers live 6000 ticks by default; medicine / weapons / apparel pass 6000 and food passes 2500; `TickIfDue` scans every 60 ticks. On expiry, map loss, or destruction, rot is restored and `RollbackOrWarn` returns the item to the ledger via the source channel (failure only `Warn`s); being picked up / worn / equipped / placed into a container counts as claimed. Cooldown is 600 ticks for the same Pawn + same def; the offer table caps at 512, beyond which that materialization is not registered, not frozen, and not reclaimed on timeout.
- **Virtual leg**: only the weapon bridge tries preserved first when vanilla has no weapon, then tries virtual via `SDS_OfferBridge.TryOfferVirtual` (also 6000 ticks); the other four categories use only the preserved leg. The offer table, landing spots, cooldown, and rot freeze exist in exactly one copy; `SDS_PreservedOffer` must not build a second one.

## 5. Third-Party Support

> Positioning: the three dedicated host implementations this module provides for third parties, where each one forwards to, and the isolation boundary between Vanilla and `SDS.ThirdModCompat`. Rules are in ModuleRules.en.md 6.4 / 6.6 and E6 / E7; host slot roles are in §2.2.

### 5.1 The Three Dedicated Host Implementations

| Host interface | Vanilla implementation | Forwards to | Why third parties need it |
|---|---|---|---|
| `ISDS_DisplayQuery` | `SDS_DisplayAdapter` | `SDS_OutputUtility.TryGetDisplayKey` | display thing identity is sealed at factory creation (container rows re-sealed at load); third parties cannot infer the channel from a display thing |
| `ISDS_DepositJobs` | `SDS_DepositJobsAdapter` | `SDS_DepositService` / `SDS_ChipManualDeposit` | job-based hauling Mods should only forward the sole deposit service and not build their own destination decisions |
| `ISDS_TransportLoadSink` | `SDS_TransportLoadAdapter` | `SDS_TransportVirtual.InjectIntoTransporters` | Mods with self-built loading UIs can only inject display-thing rows at list construction (W50) |

- **`SDS_DisplayAdapter` (display thing identity sealing)**: `IsDisplay(Thing)` and `TryGetDisplayKey(Thing, out SDS_StockKey)` both route to `SDS_OutputUtility.TryGetDisplayKey`, which consults the `displayKeys` table written by the display thing factory (`SDS_CompatHosts.cs`, `SDS_OutputUtility.cs`). Display things are projections and do not copy color / style / job tags / fuel / charge or other instance state; inferring the channel with `SDS_StockKey.FromAnyThing(display)` would judge preserved items as virtual, manifesting as "visible in the list while loading / formation / trading all report none". Identity is sealed only at creation in `MakeDisplayThing` / `MakePreservedDisplayThingFrom`; after load, unsealed persisted display things inside container rows are re-sealed by `SDS_TransportVirtual.RebindLoadedDisplayKeys` (the unique preserved bucket first, then the virtual key). The sole criterion is `SDS_OutputUtility.IsDisplay`, and the sole resolution entry is `KeyOfDisplay(display, preservedBucket)`. Third parties may only ask "is this a display thing and what is its key"; they must not construct display things themselves, nor use `RequiresPreservedStorage(display)` to judge the channel.
- **`SDS_DepositJobsAdapter` (job-based hauling forwards only the sole deposit service)**: `CanTakeCandidate` → `SDS_DepositService.CanTakeCandidate`; `TryMakeJob` → `SDS_DepositService.TryMake`; `TryMakeFromInventory` → `SDS_DepositService.TryMakeFromInventory`; `IsManualDepositAvailable` → `SDS_ChipManualDeposit.PawnCanDeposit` (`SDS_CompatHosts.cs`). Mods like Pick Up And Haul have their own WorkGiver / job factories and do not go through `HaulAIUtility`; the bridge only lets them call the same `SDS_DepositService`, keeping candidate gates, destination decisions, and inventory unload job assignment in the sole implementation. `CanTakeCandidate` only answers "does the endpoint beat the vanilla best destination", and `TryMakeJob` / `TryMakeFromInventory` only produce Jobs; third parties must not modify `targetB` again, recompute quantities, or duplicate destination sorting inside the adapter (PublicAPI.en.md 4.9, 4.10).
- **`SDS_TransportLoadAdapter` (self-built loading list injection, W50)**: it first checks `host`, `host.Map`, `CompTransporter`, and `TransportersInGroup`, then calls `SDS_TransportVirtual.InjectIntoTransporters(transferables, transporters, host.Map)`; when the transport pod group is empty it falls back to the first transporter itself and continues injecting without returning false (`SDS_CompatHosts.cs`). Third-party loading UIs that bypass vanilla `Dialog_LoadTransporters` (currently registered: the CeleTech Shuttle Extension modular shuttle) have no vanilla injection point and can only inject display-thing rows at their own "list construction" return value; injection must call the sole implementation — the adapter must not take goods, reserve, deduct, or compute quantities itself. This bridge only injects `TransferableOneWay` rows; it does not decide row selection, take goods, or deduct; job assignment / pod loading / save loading still share the unified W38–W48 path. A display thing's `stackCount` is the whole-stock aggregate rather than the vanilla `stackLimit` physical stack, so third parties doing admission by whole-stack mass before loading will have a stricter precheck than vanilla (RuleIndex.en.md W50).

### 5.2 Why the Bridges Are Defined in Contracts and Implemented in Vanilla

- The display thing factory and the `displayKeys` identity table live in Vanilla (`SDS_OutputUtility`); Core no longer keeps a display thing registration table and forbids UI / `Find` / vanilla behavior entry points, so it cannot host the factory and resolution.
- Deposit job assignment and loading injection are both vanilla execution surfaces: Contracts only declares the interface shape of `ISDS_DepositJobs` / `ISDS_TransportLoadSink`; the implementation that actually creates `Job`s, writes `TransferableOneWay`, and reads `CompTransporter` can only live in Vanilla.
- ThirdModCompat is forbidden from referencing Vanilla, and Api only forwards as a facade without implementing; therefore bridges that "need Vanilla internal capabilities yet must serve the compat layer" can only be defined in Contracts, implemented in Vanilla, injected by Bootstrap, and exposed through `SDS_API`'s internal adapter bridge.
- These three slots do not enter Core's fact axes: `Display` / `DepositJobs` / `TransportLoad` serve only the Api adapter bridge and are not consumed by Core.

### 5.3 Isolation and the Sole Write Path

- Vanilla and `SDS.ThirdModCompat` do not reference each other, and the two are unconnected in the dependency matrix; Vanilla has a single Harmony ID `sizuru.sds.vanilla`, while the 9 adapters, their target packageIds, and their respective Harmony IDs all live in ThirdModCompat. Audits: `CheckAssemblyBoundaries.ps1` (reference graph + type-level public whitelist), `CheckCompatSurface.ps1` (only Api / Contracts / Diag allowed).
- Vanilla's compilable visible surface is narrow: `InternalsVisibleTo` registers only `SDS.Core → SDS.Rules` and `SDS.Vanilla → SDS.Tests`, and the vast majority of implementation classes are internal; public types face Bootstrap host assembly, Defs XML, and saves, and are not external contracts.
- There is only one write path (E7): the same third-party entry either calls `SDS_API` or is translated by an adapter — both must not be active simultaneously; read-only projections may coexist with adapter translation. Bypassing `SDS_API` bypasses Api's caller gates (player faction, ownership, forbidden, same map) and may write non-player-faction or cross-map items into the ledger; if Harmony / reflection direct calls into Vanilla services are combined with keeping one's own job assignment, double deduction, double reservation, or two rollback orders can occur; and these calls are not covered by `SDS_API.Version`'s compatibility promise — Vanilla implementations may be refactored as Core contracts adjust (PublicAPI.en.md 3.4, 3.8, 4.3, 4.11).

### 5.4 Third-Party Types That Cannot Integrate or Can Only Partially Integrate

- **Mods with their own storage groups / self-built SlotGroups**: cannot integrate as SDS endpoints — such storage groups are usually exposed via `ISlotGroupParent`, which `ISDS_StorageEndpoint` explicitly forbids implementing (otherwise the container branch of vanilla hauling can never hold; interface comment in `SDS_Buildings.cs`), making the two mutually exclusive under vanilla contracts. There is also no third-party storage-group registration entry: Version 2 removed `SDS_API.RegisterWarehouseContainer` (no internal callers, no third-party adoption records). Coexistence is still possible: third-party storage groups participate in `TryFindBestBetterStorageFor` via vanilla `IHaulDestination` / `SlotGroup`, competing side by side with endpoints, but SDS virtual stock will not enter their groups; if such a Mod only iterates `AllGroupsListInPriorityOrder` or uses a hardcoded container table, it will not see the endpoints. Contract-layer conclusion; no actual integration instances registered at present.
- **Hauling Mods with their own job factories that bypass HaulAIUtility**: the function-level exits cover only `HaulToStorageJob` / `HaulToCellStorageJob` / `HaulToContainerJob`; Mods with their own job factories that do not call these functions are not covered and need the Mod's own `SDS_ModCompat_*` adapter going through the `ISDS_DepositJobs` bridge — Vanilla adds no destination special cases for individual Mods. Currently only Pick Up And Haul's job-type integration is registered.
- **Mods with their own loading UIs / custom lists**: only when an injection point exists at their "list construction" return value can `ISDS_TransportLoadSink` (W50) be used; if they internally construct loading Jobs directly without returning a `TransferableOneWay` list, there is no injection point. Even when integrable, only display-thing rows are injected — no takeover of loading Jobs, no deduction, no reservations; the stricter precheck is a known boundary.
- **Mods with their own display things / identity systems**: display thing identity is sealed only at factory creation in `SDS_OutputUtility` (persisted display things inside container rows are re-sealed by `SDS_TransportVirtual.RebindLoadedDisplayKeys` at load); display things constructed by third parties themselves can only fall back to `FromThing` and cannot guarantee a correct channel; the correct approach is to query `ISDS_DisplayQuery`, or use display things produced by the Vanilla factory in its own lists.
- **Target Mod not installed / not loaded**: adapters are scanned by Bootstrap step 4 for `ISDSCompatAdapter`, and `Apply` happens only when the target is loaded; not installed is silent and produces no hook points, and when not loaded no third-party patches are applied.

## 6. Supplementary Contact Surfaces (vanilla mechanism details)

- **Preserved consumption bridge timing**: offer lifetime caps at 6000 ticks by default (medicine / weapons / apparel) and 2500 ticks for food; `TickIfDue` scans every 60 ticks; cooldown is 600 ticks for the same Pawn + same def. There is no separate "return wait" timer: on expiry / map loss / destruction the item returns to the ledger via the source channel directly, and a failed return only `Warn`s.
- **Bridge boundary**: landing spots are no longer tracked once merged; when a reservation already exists for the category, the whole category is skipped without repeated materialization.
- **Post-materialization handling**: materialized instances are immediately marked, `SetForbidden(false)`, and have `CompRottable` frozen, avoiding rotting or being forbidden right after landing.
- **Use command timing**: materialization → determination → return all complete within the same UI callback, with no residue at frame end and no new save fields.
