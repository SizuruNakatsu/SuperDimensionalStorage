# SDS.Vanilla · Design Decisions (why things are done this way / pitfalls encountered)

> Positioning: this file preserves the complete reasons for "why this module does things this way" — historical decisions, pitfalls encountered, differences between the old and new implementations, and design trade-offs. It records reasons only and does not restate checkable rules.
> For rule text (including the rule ID summary and the mirror visibility conclusions) see [Rules.en.md](Rules.en.md) §10 / §11; for patch counts and file distribution see PatchInventory.en.md.

## 3. Design trade-offs

> The former ImplementationRationale.md was merged in full into this section: former §1 → 3.1, former §2 → 3.2, former §3 → 3.3 (item numbers 1–6 retained; the "basis" column of [Rules.en.md](Rules.en.md) V5, which reads "ImplementationRationale.md 3.1", refers to item 1 of this section); former §1.4 (the old file location table, duplicating §1), former §4 (maintenance constraints), and former §6 (acceptance focus points) duplicated [Rules.en.md](Rules.en.md) and [Interfaces.en.md](Interfaces.en.md) and have been deleted.

### 3.1 Why vanilla adaptation must be a separate assembly

- Patch ownership is fixed by ModuleRules.en.md §7: the attribute patch classes are all in Vanilla, and so are the 29 registry entries (19 mirror guards + 10 projection owners); the 9 third-party adapters' patches are dynamic `harmony.Patch` calls inside `SDS.ThirdModCompat` and are not counted.
- `SDS_PatchInstaller` scans only the `SDS.Vanilla` assembly, calling `CreateClassProcessor(type).Patch()` class by class, and scans no other assemblies; the other layers are forbidden by the rules from taking on this job: Contracts bans Harmony (6.1), Core bans Harmony and all vanilla behavior entry points (6.3), Api bans Harmony (6.5), Bootstrap handles only installation and the startup order (6.7, §9), and ThirdModCompat's Harmony targets only specific third-party goals.
- The installation order also fixes this: startup step 3 installs `SDS_PatchInstaller` first (attribute classes + the two registries), and only step 4 scans third-party adapters; even with no third-party mods at all, the vanilla seams must take full effect (ModuleRules.en.md §9).
- Per-class try/catch: on failure it only logs a `Warn` and continues; the startup report outputs "A/B = applied / declared" plus the failure list, and the A/B figures can be matched directly against `CheckPatchInventory.ps1` (`SDS_PatchInstaller.cs`; ModuleRules.en.md §11). Patch counts, registry counts, and patch class names can therefore serve as acceptance items.
- Separating facts from rules is what lets Core be tested outside the game startup flow: Core is forbidden from calling vanilla behavior surfaces such as `ListerThings`, `GenClosest`, `ResourceCounter`, `JobDriver`, `SlotGroup`, `Reachability`, `IHaulDestination`, `IThingHolder`, `Find.*`, `mapPawns`, `GenPlace`, `GenSpawn` (ModuleRules.en.md 6.3), so these facts can only be injected through `SDS_Host`; of the 11 slots only Ports / DepositFilter / Delivery are still consumed directly by Core, Priority / MirrorPhysical / MedicalCare are instead injected by callers as query fields / plan fields / delegates, MirrorQuery belongs to the Api adapter bridge, ReclaimWorld is used only inside this module since C1, and Display / DepositJobs / TransportLoad serve only the Api adapter bridge (ModuleResponsibilities.en.md §3, §5, §6). Host implementations have public parameterless constructors and read live state on every call, so `SDS_Host.Install` may run before `SDS_GameComponent_Grid`, and the test side can fill every slot with fake implementations. "Outside" only means not starting the game at runtime, not building a `Map`, and not entering the mod startup sequence; compilation still references RimWorld / Verse data types (ModuleRules.en.md §4).
- Third-party compatibility does not pollute this layer: Vanilla references only Contracts / Diag / Core / Harmony, ThirdModCompat references only Contracts / Diag / Api / Harmony, and the two never reference each other (ModuleRules.en.md 2.3, §4); Vanilla contains no target mod's packageId, type names, or adapter branches; adding or removing a third-party adapter requires no changes to Vanilla and does not change the A/B figures of the vanilla seam patches.

### 3.2 Why the attribute patches and registries must stay in this layer

- For counts and ownership see [Rules.en.md](Rules.en.md) V4 and the statistics section of PatchInventory.en.md; this document does not restate the numbers.
- The two registries are not C# attribute classes but entry points mounted dynamically via `TargetMethod()` by `SDS_MirrorGuardRegistry` / `SDS_ProjectionOwnerBridge` during the Vanilla installation phase; they likewise depend on vanilla types and methods and can only stay in Vanilla together with the attribute patches (`SDS_PatchInstaller.cs`; ModuleResponsibilities.en.md §6).
- Patches and registries provide only "vanilla facts and execution": identifying mirrors, rewriting visibility, converting distances, forwarding job assignment, and writing through on the endpoint buffer; they do not define deduction, reservation, capacity, sorting, or rollback rules.
- For how many patch classes each file holds, see the statistics section of PatchInventory.en.md; this layer does not duplicate the vanilla behavior entry point table in ModuleResponsibilities.en.md §6.
- Acceptance focus points: patch A/B, 19 mirror guards + 10 projection owners, the 16 static cleanup items, save node names and `LookMode` (renaming is L3) — for how to check them see [Rules.en.md](Rules.en.md) V4 / V8 / V10 and §6.

### 3.3 Six key trade-offs

1. **Vanilla seams rely mainly on Postfix + explicit low priority.** Entry points such as the resource readout, wealth, Map-level holders, hauling job assignment, and drop-cell guards are uniformly marked `[HarmonyPriority(Priority.Low)]`, letting other mods see the vanilla result first and then decide whether to add mirrors, add job assignments, or yield (`Patch_VanillaSeams.cs`). The only exception is the Prefix on `ResourceCounterTick`: it only triggers one throttled `UpdateResourceCounts()` call and does not change the vanilla return value (same file, `Patch_SDS_ResourceCounterFastRefresh`).
2. **Take over only when the vanilla result is missing or suboptimal.** `JobGiver_Haul` adds an assignment only when the vanilla `__result == null`; `HaulToStorageJob` is replaced only when endpoint resolution wins, otherwise the vanilla result (including vanilla null) is kept; the mirror fallback of `WorkGiver_DoBill` runs only after the vanilla search finds no ingredients; the preserved consumption bridge materializes only 1 thing when the vanilla decision returns "none" (PatchInventory.en.md §4, §6.5). Not "rewrite every entry point", but keep vanilla behavior as the baseline.
3. **Mirror physical operations forbid `SplitOff` / `TryAbsorbStack`.** For reasons and checks see §1.3 and [Rules.en.md](Rules.en.md) §4; partial pickups only change `stackCount` and use the product of `SDS_OutputUtility.MakeDisplayThing`, while whole-stack pickups only do `ForgetMirror` / `Unmark` / restore `CompRottable.disabled` / `DeSpawnOrDeselect` (ModuleInterfaces.en.md 4.3; `SDS_Mirrors.cs`).
4. **`SDS_GameComponent_Grid` no longer implements `IThingHolder`.** Preserved true bodies are held by the private owner of `SDS_Ledger`; the grid only creates the ledger, calls `ExposeData` / `Tick`, sets `Instance`, and calls `SDS_Core.Attach`. `Verse.Map.GetChildHolders` iterates `map.components`, and `GameComponent` is not in that collection, so removing `IThingHolder` has no effect on Map-level enumeration; if other callers are discovered, fall back to an empty owner / read-only view rather than exposing a mutable owner (ModuleInterfaces.en.md 4.1; `SDS_GameComponent_Grid.cs`).
5. **Host implementations do not cache cross-save state.** `SDS_VanillaServices` / `SDS_EndpointProvider` / `SDS_DisplayAdapter` etc. are process-level instances that read `Instance?.State` on every call and read no `Instance` / `State` / `Find` / `Def` at construction; this decouples the injection order (startup step 2) from save shell construction (step 7) (ModuleInterfaces.en.md 4.2; `SDS_VanillaServices.cs`, `SDS_EndpointProvider.cs`, `SDS_CompatHosts.cs`).
6. **The save shell only serializes content; it does not fall back to rebuilding the ledger.** `ExposeData` calls `Ledger.ExposeData()`, `State.ExposeData()`, and the component-level `sdsReclaim` (the reclaim ledger); silent reconstruction would lose saves and would not re-attach `SDS_Core` (ModuleRules.en.md §5; ModuleInterfaces.en.md 4.1).

> This chapter reflects the current design trade-offs; maintaining this module no longer requires reading any historical archives.

## 4. Additional decisions and pitfalls

> The following fifteen entries are trade-offs confirmed as "still valid, with reasons not covered by the first three sections" after re-reviewing the old design; they record why only, without restating rule text.

| # | Decision / Pitfall | Status / Rationale |
|---|---|---|
| 1 | The mirror-building criterion accepts only "non-preserved + resolved + count > 0"; the "rebuildable" test must not be used to filter virtual entries from old saves, otherwise entries kept in the ledger would vanish entirely from vanilla search, withdrawal, and wealth after an upgrade | `SyncAll` skips `key.preserved`, `!key.Resolved`, and `count <= 0`. Unresolved entries get no mirror and do not enter `ListerThings` / `ThingGrid` / `Region` / `GenClosest`; they remain only in the unresolved area of the storage window; the ledger entry is kept and automatically recovers on the next sync once the def comes back. At generation the mirror stack count is first set to `Math.Min(count, stackLimit)` and the mirror is spawned afterwards; only on success is the mirror `stackCount` written back to the full count — vanilla `Thing.SpawnSetup` truncates over-limit stacks, so writing the real value first would be silently truncated; the ledger itself is not written by the mirror-building path |
| 2 | Structure departure (vault `DeSpawn` / map unload) is not a pickup entry point, but projections must be withdrawn first: the vanilla relocation loop calls `SplitOff` on over-limit stacks in the cell, and a mirror's `SplitOff` would be translated into pickup deductions | Both entry points call `EvacuateForStructureChange` before `base.DeSpawn` / `Deinit`. Evacuation only removes markers and `Destroy(Vanish)`es mirrors — zero ledger writes, no real things produced, no count changes; it uses a locally collected list rather than a static table (`Destroy` may re-enter through events), is a no-op on an empty list, and can be repeated. Between evacuation and the next rebuild, read-side consumers (availability / wealth / trading / resource readout) fall back to the ledger, and counts do not drop just because the window has no mirrors |
| 3 | Single-cell self-healing is not the same as structure departure: `EdificeGrid.DeRegister` does not verify that "the thing being deregistered is itself"; any building leaving the cell clears the vault slot, leaving the vault present but with `GetMaxItemsAllowedInCell` falling back to 1 | `RepairEdificeRegistration` re-`Register`s the vault when no other building is in the cell, without rebuilding the building. Vault relocation can only take the full `DeSpawn` + `GenSpawn.Spawn` path; clearing the cell with a bare `DeSpawn` does not work — during gameplay a mirror's `DeSpawn` is intercepted by the guard (only evacuation / map unload is allowed through), and vanilla `GenSpawn` moving items within the same cell would conflict with the DeSpawn protection of leftover projections, raising the `already spawned` red error. Before a mirror takes a cell it first checks `GetMaxItemsAllowedInCell <= GetItemCount`; if unsatisfied it does not spawn and calls `ScheduleRetry()` |
| 4 | The global storage priority is save-level, not a mod cross-save setting; `-1` is the "never set in this save" sentinel, not an actual priority | The sole read/write point is `SDS_VanillaState.CoreStoragePriority` / `SetCoreStoragePriority`: the read side falls back to mod settings only when it sees `-1`, and the UI does not write `SDS_Config` directly. Why it lives in the save: changing the priority in the core UI happens in-game and does not trigger the mod settings' `WriteSettings`; writing memory only would lose it to "Normal" after a restart. It is already effective at load-time `FinalizeInit` (endpoint `SpawnSetup` syncs `StorageSettings.Priority`), and the 250 tick full scan only performs fallback correction |
| 5 | Trading / caravan formation / loading lists do not create cross-dialog reservations; they settle only at the deal / departure / load-onto-cart moments | Reservations count into `SDS_Availability.GetAvailableCount` (Total − Reserved); if lists deducted reservations early, rows that still have stock would compute to 0 and gray out — players would see "in stock but unclickable". Opening a list reads a snapshot only, and settlement opens one transient transaction; another job's reservation still blocks availability, which is intentionally conservative |
| 6 | `Pawn_JobTracker.CleanupCurrentJob` is private, so Harmony can only hook it by its private name; and when `releaseReservations && !carryThingAfterJob`, vanilla drops the `carryTracker` items on the ground | "Suspend / end without dropping goods" holds only for `inventory` (the deposit job goes through the inventory). The Prefix of `Patch_SDS_ReclaimJobTargets` calls `SDS_ReclaimRegistry.ReclaimHand(pawn, loadID)` to reclaim carried materials before the vanilla cleanup drops them; `SDS_DepositJobCleanup` only looks at `pawn.inventory.innerContainer` and cannot reach `carryTracker`, so carried items must be handled separately |
| 7 | The preserved consumption bridge's timing constants are not arbitrary: 6000 / 2500 ticks are the offer timeout caps, and 600 ticks is the offer cooldown per Pawn + per def | 6000 ticks is about 1.7 in-game hours, enough to walk from an access point and complete one withdrawal; food uses 2500 because eating usually happens nearby. 600 ticks keeps high-frequency thinking from repeatedly materializing / reclaiming. When the drop cell merges into an existing same-kind stack on the map, the instance is already destroyed and the count conserved, so tracking / marking / unforbidding no longer applies; a candidate category is skipped entirely as long as it has any reservation (`GetReserved > 0`), because reservations are key-level and there is no guarantee that the item taken is not the one someone else reserved |
| 8 | In the old version (2.5.2), the endpoint input buffer did not remove items from `inputBuffer` after a successful deposit, so the same true body was written into both `preservedThings` (Deep) and `inputBuffer` (Deep), and on load Scribe reported `Id already used` | The write side was changed to `RemoveIfContained` after a successful deposit; the read side adds `PruneLoadedBuffer`, removing duplicate copies by `thingID`. **You cannot rely on `holdingOwner` alone**: in old saves the buffer copy and the preserved true body are two objects with the same ID, and only ID-level checking can identify this |
| 9 | Load-time mirror cleanup must not be placed in `SDS_VanillaState.ExposeData/PostLoadInit` | That timing is earlier than map spawn; destroying first would make the map loading phase spawn again from the save, producing `Spawning destroyed thing / 0 stackCount`. The old version cleaned up in `SDS_GameComponent_Grid.FinalizeInit`, when the map was already ready, so it had no such problem |
| 10 | Do not restore the old same-tick job assignment decision cache (`SDS_HaulJobDecisionCache`) | In the new architecture, hauling dispatch calls `SDS_DepositService.TryMake` at only two single points, `JobGiver_Haul.TryGiveJob` and `HaulAIUtility.HaulToStorageJob`, with no old-style paired duplicate decisions between `HasJobOnThing ↔ JobOnThing`; restoring the old cache would create a second piece of cross-call state and instead increase inconsistency risk |
| 11 | The map signature / stock nudges were changed to 30 ticks, and the safety net notifies mirrors only when changed | Neither the map set nor the stock version needs tick-by-tick awareness; a 30 tick delay is far smaller than the wealth 300 / apparel 600 debounces. `Reconcile` already compares `Operational`, so unconditional 250 tick mirror re-evaluation is idle spinning; fetching buildings by the 3 SDS defs reduces a whole-base scan to 3 short lists |
| 12 | Channel separation is implemented via "file ownership + two-way reference ban", not by splitting the assembly in two (the 2026-11-16 review rejected splitting `SDS.Vanilla` into virtual / preserved assemblies) | Port buildings / Hyperdimensional Space UI / the save shell / the reclaim queue / unified vanilla hook points must be shared per Guideline 1 and Corollary 3 — splitting the assembly in two would create dual ledger write paths and double patches on the same vanilla method, and channels are judged per "thing" at runtime and cannot be grouped by item a priori (the only judgment lives in `SDS.Rules.RequiresPreservedStorage`; copying it twice would violate Guideline 3). The only thing that can be hardened is the direct dependencies of `Mirrors/` and `Preserve/`: the `CheckAssemblyBoundaries.ps1` §10 two-way reference ban (Rules.en.md §14). To this end, the virtual mirror ingredient fallback was physically moved from `SDS_PreservedBill.cs` into the shared layer `Jobs/SDS_VirtualBillFallback.cs` (including the vanilla ingredient reflection probes `findInSet` / `findInSetNoMix` and `RootCell` shared by both channels; the preserved side only calls them and never overrides); the dual-channel hook point `Patch_SDS_PreservedBillIngredients` stays in `Preserve/`, and the virtual leg only calls the shared layer. Member bodies were moved verbatim with zero changes to the public surface / patch points / behavior (`SDS.Tests` all green). The same day, per Plan B, the offer table, drop cells, rot freezing, timeout return-to-storage, and the virtual leg of `SDS_PreservedOffer` were physically moved to `Foundation/SDS_OfferBridge.cs`, leaving only the preserved offer selection and the five hook point categories in `Preserve/`; there is still one offer lifecycle, and no second cache is added |
| 13 | W47's load-time reconstruction adds no save nodes and does not persist runtime plans to disk | The reservation ledger stores only "unique key + total count"; container rows are restored by W48; before materializing, the JobDriver rebuilds the plan via `TakePlan` from the **unique** grouping bucket for the reservation key inside the container, failing closed on multiple buckets with the same key / missing bucket / insufficient quantity. Rationale: runtime plans do not cross saves (Guideline 3), and ledger reservations are the sole authority; persisting plans or instance IDs would create a second authority, and modifying `SDS_Reservation` / `SDS_TransportLoadSave` is an L3 save-structure change whose benefits do not outweigh the risks. `FinalizeInit` immediately attempts one W48 row restoration to shorten the JobDriver's waiting window |
| 14 | Display thing identity is sealed only at the factory; load-time re-sealing is added, and no structural fallback is kept on hot paths | `displayKeys` are not persisted. `FinalizeInit` calls `SDS_TransportVirtual.RebindLoadedDisplayKeys` after W48 restoration: for persisted display things inside container rows that are not spawned and have no holder, it resolves first by the unique preserved bucket, then re-seals by the virtual key; when multiple buckets share a key and cannot be uniquely resolved, the thing stays unbound and fails closed as a non-display thing. Rationale: a structural fallback would treat any unspawned / holder-less Thing as a display thing, violating "identity is determined only when sealed"; the inventory is untouched, so there is no fallback to guessing |
| 15 | Bucket identity / key resolution are consolidated to single points, and registries are separated per flow | `SDS_PreservedBuckets.SameBucket` is the sole judgment for W45; `SDS_OutputUtility.KeyOfThing` is the sole helper from instance → category key; `SDS_DisplayBucketRegistry` provides the sole registration / lookup / removal / cleanup implementation, with trading, caravan transport, and loading each holding one instance. Rationale: judgment and key resolution must be unique; registries differ in lifecycle and cross-container isolation, and merging them into a global singleton would let one flow's refresh mistakenly clear another flow's registrations |
| 16 | Mirror job targets cannot rely on third-party adapter fallbacks: VEF PipeSystem's `BringToProcessor` bare-reads `Ingredient.def` inside Job-level endCondition / finalizer, and after mirrors go stale on load it throws NREs endlessly | Fix our own generic seam instead of adding an adapter: on W60 key invalidation, first end the current job / dequeue from queues / remove queue slots, then drop the target; runtime mirror removal goes through the same consolidation point beforehand; after load, sync immediately + remap immediately. Rationale: mirrors are equivalent to a real warehouse, and real items do not turn null mid-job; this is the common precondition of all "carry the target away first, use the target reference later" drivers. Per SDS.ThirdModCompat/Rules.en.md §5.4, no adapter is added for a single mod, and an adapter cannot cover the "mirror removed before saving" path; after pickup the vanilla `Toils_Haul.StartCarryThing` already rewrites the job slot to the true body, so the pickup primitive needs no change. Boundary: slots already turned null in old saves cannot be fixed side-effect-free before a third-party finalizer; this fix only guarantees that new saves no longer produce that state, and already-broken saves need one manual job cancellation. Implementation consolidation: slot enumeration / queue add-remove / end-dequeue actions / mirror liveness each exist exactly once (`SDS_MirrorJobTargets`, `SDS_MirrorService.IsLiveOn`); before rewriting/consolidating a loaded entry, verify that the slot still points at the old mirror (already `Destroyed`) or has gone invalid as null, and skip when the job has already advanced (vanilla `StartCarryThing` has already swapped the slot for the carried true body), avoiding overwriting real targets or ending jobs by mistake; save entries do not record the old `thingID`, so `Destroyed` is an approximation (making it precise requires save-structure changes, which is L3 and not done); invalid mirror replacement has been changed to "create the new mirror first → repoint exact references → then remove the old mirror", so the success path no longer cancels jobs; failures in creation / cell placement / replacement still fall back to closing the old target and removing it; on repointing, the old mirror's reservation is released (the new target takes over non-exclusively per W61), and job traversal uniformly goes through `ForEachJobOnMap`; vault relocation still uses "end first", and remapping after key-based rebuild is listed as a later P1 behavior optimization |
